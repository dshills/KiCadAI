Status: offline-qualified, **not live-accepted or authorized to spend**. Reviewer: implementing Codex agent, September 13, 2026; this is not an independent review. ## Checks completed

- The strict policy decoder requires exactly `goal`, `max_requests` and integer `max_micro_usd`. Duplicate, unknown, missing, invalid and trailing fields are rejected. An explicit policy cannot select the legacy goal. CLI tests reject offline-mode budget combinations and verify policy checking before provider construction.
- A v2 ledger records the exact new goal and both caps. Neither can be altered in place. Existing v1 ledgers are not migrated, reset or extended. Missing ledger metadata does not inherit permissive defaults. Non-regular ledger files and concurrent locks are rejected. Temp-file data and parent-directory rename metadata are synced before a physical dispatch can begin.
- Each physical attempt reserves USD 0.05 permanently. Failed requests, unknown outcomes and inexpensive responses never restore allowance. In-memory transport tests prove that a fifteenth attempt cannot reach the transport, and a smaller dollar cap stops requests independently. Invalid or excessive reported usage persists a halt. The existing pinned model, HTTP endpoint, request-size/output-token bounds and no-retry policy are unchanged.
- The batch runner uses one fixed output, lock and v2 ledger path. It requires an approval record separate from the proposed policy, bound to the frozen evaluation and qualified runtime. The record must quote an actual user approval; software cannot authenticate a human approval cryptographically. No approval record exists at this checkpoint.
- Attempt identity is durably saved before child creation. Every original case stays in the 14-case denominator. The child is observed terminal before an outcome is committed. A timeout kills its process group. A stopped batch may resume only a contiguous suffix of unseen cases after the old runner is confirmed absent and prior evidence/ledger identities match. Unknown outcomes and leftover locks require separate inspection; the runner will not delete a stale lock or retry a case automatically.
- Semantic misses are retained while collection continues. Execution, accounting, protocol and native-evidence failures stop collection. Raw structured provider decisions and admitted application decisions have separate automatic checks. Local correction cannot increase the raw-model pass count. The preserved `selection.json` contains the unmodified structured decision returned by the provider adapter plus response ID/usage; it is not a claim to retain raw HTTPS bytes or the entire provider HTTP envelope.
- Automatic checks verify exact configurations, complete original clauses and consistent dispositions. They deliberately leave explanation quality, unresolved-choice relevance and requirement preservation pending explicit semantic review. A generic question or incomplete refusal cannot be accepted merely because its disposition matches. The final review must address every frozen case's question/reason condition for both raw and admitted decisions.
- Supported output checks authenticate the complete 14-gate record, native hashes and manufacturing manifest, and compare every required native/BOM/library/configuration/electrical/preview/manufacturing deliverable to the reviewed example. Only the pre-existing explicit timestamp fields are normalized, in memory. Non-design responses must contain only selection evidence, with no generated board. A valid but wrongly selected configuration is a semantic miss, not a repaired success.
- Timing includes all five supported attempts, including failed or unknown outcomes. Missing timing prevents the target from passing. Collection completion is not acceptance: semantic review and the complete 14/14 protocol requirements remain necessary.
